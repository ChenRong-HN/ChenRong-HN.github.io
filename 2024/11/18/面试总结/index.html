面试总结

  1. IOC：

    将一个复杂系统分成若干个独立的部对象，将各个对象的类进行封装并且内部实现对外是透明的，从而降低了解决问题的复杂度。引入第三方（IOC容器）实现具有依赖关系的对象之间松耦合，如下图：

    使得A、B、C、D之间没有了耦合关系，全部对象的控制权交给了第三方（IOC容器）。在开发的时 候每个成员只需要完成的自己的类就行了。

    我们再来看看，控制反转(IOC)到底为什什么要起这么个名字？我们来对⽐一下：

    软件系统在没有引⼊入 IOC 容器器之前，对象 A 依赖于对象 B，那么对象 A 在初始化或者运行到某一点的时候，自己 必须主动去创建对象 B 或者使⽤用已经创建的对象 B。无论是创建还是使用对象 B，控制权都在自己手上。 软件系统在引入 IOC 容器器之后，这种情形就完全改变了了，由于 IOC 容器器的加入，对象 A 与对象 B 之间失去了直接 联系，所以，当对象 A 运行到需要对象 B 的时候，IOC 容器器会主动创建一个对象 B 注入到对象 A 需要的地⽅。 通过前后的对比，我们不难看出来：对象 A 获得依赖对象 B 的过程，由主动行为变为了了被动行为，控制权颠倒过 来了，这就是“控制反转”这个名称的由来。

  2. spring中bean的生命周期：

    1. 实例化（Instantiation）：当容器加载配置文件时，会根据配置信息创建 Bean 的实例。这通常发生在容器启动阶段。
    2. 属性设置（Property Setting）：在实例化完成后，容器会通过依赖注入（Dependency Injection）或者通过调用显式配置的 setter 方法来设置 Bean 的属性。
    3. 初始化（Initialization）：在属性设置完成后，Spring 容器会调用初始化方法对 Bean 进行初始化，这个过程可以通过配置 XML 文件中的 init-method 属性或者使用 @PostConstruct 注解来实现。
    4. 使用（In Use）：初始化完成后，Bean 就可以被容器使用了，它可以被注入到其他 Bean 中，或者通过容器的 getBean() 方法获取并使用。
    5. 销毁（Destruction）：当容器关闭时，或者通过配置 XML 文件中的 destroy-method 属性或者使用 @PreDestroy 注解来声明销毁方法时，容器会调用销毁方法对 Bean 进行清理工作，释放资源等。

    这些阶段构成了 Spring Bean 的完整生命周期。在这个过程中，Spring 容器负责管理 Bean 的创建、初始化、使用和销毁，开发者可以通过配置和编码来控制 Bean 的生命周期，以满足不同的需求。

  3. spring中单例bean的线程安全问题：

    因为成员变量是存放在堆内存中，而堆内存又是线程共享的，这就造成了 线程安全问题。spring中的bean默认是单例模式的，所以在定义成员变量时有可能会发生线程安全问题。

    原型Bean：每次创建一个新对象，也就是线程之间并不存在bean共享，所以不会有线程安全问题

    单例Bean：对于单例bean，所有线程都共享一个单例bean，因此存在资源的竞争，如果单例bean是一个无状态bean，也就是线程中的操作不会对bean的成员执行查询以外的操作，那么这个单例bean是线程安全的；对于有状态的bean，Spring官方提供的bean一般提供了通过ThreadLocal去解决线程安全的方法，比如RequestContextHolder、TransactionSynchronizationManager、LocaleContextHolder等。

    注：Spring容器本身并没有提供线程安全的策略，因此是否线程安全完全取决于Bean本身的特性

    使用ThreadLocal的好处：使得多线程场景下，多个线程对这个单例Bean的成员变量并不存在资源的竞争，因为ThreadLocal为每个线程保存线程私有的数据

  4. 为什么MySQL InnoDB存储引擎用B+树做索引：

    1. B+树空间利用率更高，可减少I/O次数：一般来说，索引本身也很大，不可能全部存储在内存中，因此索引往往以索引文件的形式村塾的磁盘上。这样的话，索引查找过程中就要产生磁盘I/O消耗。而因为B+树的内部节点只是作为索引使用，而不像B树那样每个节点都需要存储硬盘指针。也就是说，B+树每个非叶子节点没有非叶子没有指向某个关键字具体信息的指针，所以每一个节点可以存放更多的关键字数量，即一次性读入内存所需要查找的关键字也就越多，减少了I/O操作。
    2. 增删文件时，效率更高：因为B+树的叶子节点包含所有关键字，并以有序的链表结构存储，这样可很好提高增删效率，基于范围查询更好。
    3. B+树的查询效率更加稳定：因为B+树的每次查询过程中，都需要遍历从根节点到叶子节点的某条路径。所有关键字的查询路径相同，导致每次查询的效率相当。

  5. MyISAM和InnoDB存储引擎：这是MySQL中最常用的两种存储引擎，它们对索引的实现方式是不同的。

    • MyISAM：

      data存的是数据地址。索引是索引，数据是数据。索引放在XX.MYI文件中，数据则在XX.MYD文件中，所以也叫非聚集索引（记忆：分散存储）。

    • InnoDB引擎：

      data存的是数据本身。索引也是数据。数据和索引存在一个XX.IDB文件中，所以也叫聚集索引（记忆：都放在一块）。

    • 区别：

      1. MyISAM是非事务安全的，而InnoDB是事务安全的

      2. MyISAM锁的粒度是表级的，而InnoDB支持行级锁和表级锁（默认行级）

      3. MyISAM支持全文类型索引，而InnoDB不支持全文索引

      4. MyISAM相对简单，效率上要优于InnoDB，小型应用可以考虑使用MyISAM

      5. MyISAM表保存成文件形式，跨平台使用更加方便

      6. MyISAM管理非事务表，提供高速存储和检索以及全文搜索能力，如果在应用中执行大料select操作可选择

      7. InnoDB用于事务处理，具有ACID事务支持等特性，如果在应用中执行大量insert和update操作可选择

        行锁和表锁的区别：

        • 行锁是对单行数据进行锁定，表锁是对整个表进行锁定
        • 行锁的开销大，加锁满，表锁的开销小，加锁快
        • 行锁会出现死锁，表锁不会
        • 行锁的锁定粒度小，发生锁冲突的概率低，表锁反之
        • 行锁适用于高并发的场景，表锁适用于需要保证整表一致性的场景
        • 行锁需要走索引，表锁不需要走索引

  6. 最左前缀原则：(看面试题足矣)

    • 建立一个索引，对于索引中的字段，mysql会一直向右匹配直到遇到（>、<、between、like）就停止匹配，比如a = 1 and b = 2 and c > 3 and d = 4 如果建立(a,b,c,d)顺序的索引，d是用不到索引的，如果建立(a,b,d,c)的索引则都可以用到，a,b,d的顺序可以任意调整。
    • =和in可以乱序，比如a = 1 and b = 2 and c = 3 建立(a,b,c)索引可以任意顺序，mysql的查询优化器会帮你优化成索引可以识别的形式

  7. 查询性能优化的方法：

    1. 只返回必要的列：避免使用select *
    2. 只返回必要的行：使用LIMIT语句来限制返回的数据
    3. 缓存重复查询的数据：避免直接到数据库中查询

  8. 索引的类型：

    • 普通索引：基本索引类型，允许定义的索引字段为空值和重复值
    • 唯一索引：索引的值必须唯一，定义索引的字段允许为空
    • 主键索引：索引的值必须唯一，不能为空
    • 复合索引：多个字段加索引，遵守最左前缀原则
    • 全局索引：只有在MyISAM引擎上才能使用

  9. 索引为什么使用树结构：加快查询效率，而且保持有序

1. ArrayList

数据结构与底层实现

  • 数据结构：ArrayList 底层使用动态数组（Object[]）来存储元素。
  • 实现：当数组容量不足时，ArrayList 会通过创建一个更大的数组并将旧数组中的元素复制到新数组中来实现动态扩容。

优缺点

  • 优点：
    • 快速随机访问：由于底层是数组，支持快速的随机访问（通过索引访问元素的时间复杂度是 O(1)）。
    • 内存局部性：由于存储在连续的内存区域，具有良好的内存局部性，有助于提高缓存命中率。
  • 缺点：
    • 插入和删除性能：在数组中间进行插入或删除操作时，需要移动元素，因此时间复杂度为 O(n)。
    • 扩容开销：扩容时需要复制数组，可能会有较大的开销。

使用场景

  • 适用于：频繁进行随机访问，但不经常插入或删除操作的场景。例如：实现缓存、数据读取操作等。

2. LinkedList

数据结构与底层实现

  • 数据结构：LinkedList 使用双向链表（Node 类包含前向和后向指针）来存储元素。
  • 实现：每个节点（Node）包含一个数据元素和两个指针（一个指向前一个节点，一个指向下一个节点）。

优缺点

  • 优点：
    • 高效插入和删除：在链表中间进行插入或删除操作不需要移动其他元素，只需调整指针，因此时间复杂度为 O(1)。
    • 无扩容开销：不需要动态扩容，因为不依赖于固定大小的数组。
  • 缺点：
    • 较慢的随机访问：由于需要从头节点开始遍历链表，随机访问的时间复杂度为 O(n)。
    • 较高的内存开销：每个节点需要额外的内存存储指针（前向和后向），因此总的内存开销较大。

使用场景

  • 适用于：频繁进行插入和删除操作，但不经常进行随机访问的场景。例如：实现队列、双端队列等。

3. Vector

数据结构与底层实现

  • 数据结构：Vector 的底层实现与 ArrayList 相似，也是使用动态数组（Object[]）。
  • 实现：Vector 在扩容时与 ArrayList 类似，但默认的扩容策略是每次扩容时增加原容量的 100%。

优缺点

  • 优点：
    • 线程安全：Vector 的所有方法都是同步的，因此是线程安全的。
    • 动态扩容：类似于 ArrayList，支持动态扩容。
  • 缺点：
    • 性能开销：由于方法是同步的，Vector 的性能可能不如 ArrayList，尤其是在单线程环境下。
    • 较大的扩容增量：默认的扩容策略可能导致内存使用效率较低。

使用场景

  • 适用于：需要线程安全的动态数组的场景。不过，现代应用中更推荐使用 Collections.synchronizedList(new ArrayList<>()) 或 CopyOnWriteArrayList 代替 Vector。

总结与比较

特性 ArrayList LinkedList Vector
数据结构 动态数组（Object[]） 双向链表 动态数组（Object[]）
随机访问 快速（O(1)） 慢（O(n)） 快速（O(1)）
插入/删除 慢（O(n)） 快速（O(1)） 慢（O(n)）
扩容开销 复制数组 不涉及扩容 复制数组
线程安全 否 否 是（方法同步）
内存开销 较小 较大 较小（与 ArrayList 相似）
使用场景 频繁读操作，偶尔写操作 频繁写操作，偶尔读操作 需要线程安全的场景

选择 ArrayList、LinkedList 或 Vector 取决于具体的应用场景和性能需求。ArrayList 适用于需要快速随机访问的场景，LinkedList 适用于频繁插入和删除操作的场景，而 Vector 适用于需要线程安全的动态数组场景，但在现代应用中更推荐使用 Collections.synchronizedList 或 CopyOnWriteArrayList。

Set常用的子类

Set接口在Java中表示一个不包含重复元素的集合，其主要实现类有HashSet、TreeSet和LinkedHashSet。

  1. HashSet
    • 数据结构：基于哈希表实现，内部通常采用HashMap作为底层数据结构。
    • 特点：无序性，即元素不按特定顺序排列；唯一性，即集合中每个元素都是唯一的。
    • 性能：由于基于哈希表，HashSet在添加、删除和查找元素时具有较高的性能，平均时间复杂度为O(1)。
    • 使用场景：适用于需要快速查找、添加和删除元素，且不关心元素顺序的场景。
  2. TreeSet
    • 数据结构：基于红黑树实现，一种自平衡的二叉搜索树。
    • 特点：有序性，即元素按照自然顺序或者自定义的Comparator进行排序；唯一性，即集合中每个元素都是唯一的。
    • 性能：添加、删除和查找元素的性能为O(log n)，相对HashSet稍慢，但保证了元素的排序顺序。
    • 使用场景：适用于需要按照特定顺序排列元素的场景，如排序、范围查找等。
  3. LinkedHashSet
    • 数据结构：结合了哈希表和链表的特点，通过链表维护元素的插入顺序。
    • 特点：有序性（指插入顺序），即元素按照插入的顺序进行排列；唯一性，即集合中每个元素都是唯一的。
    • 性能：相对于HashSet，LinkedHashSet在插入、删除和查找元素时的性能略低，因为它需要维护元素的插入顺序。但相对于TreeSet，其性能通常更高。
    • 使用场景：适用于需要按照插入顺序访问元素，且要求元素唯一的场景。

Map常用的子类

Map接口在Java中表示一个存储键值对的集合，其主要实现类有HashMap、HashTable、TreeMap和ConcurrentHashMap。

  1. HashMap
    • 数据结构：基于哈希表实现，允许使用null键和null值。
    • 特点：无序性，即键值对不按特定顺序排列；键的唯一性，即每个键只能对应一个值。
    • 性能：具有较高的性能，在理想情况下，添加、删除和查找操作的时间复杂度为O(1)。
    • 使用场景：适用于需要快速查找、添加和删除键值对，且不关心键值对顺序的场景。
  2. HashTable
    • 数据结构：与HashMap类似，但它是线程安全的，通过在方法上添加synchronized关键字实现同步。
    • 特点：无序性；键的唯一性；线程安全。
    • 性能：由于线程同步的开销，HashTable的性能通常低于HashMap。
    • 使用场景：在多线程环境下，当需要保证线程安全时，可以考虑使用HashTable，但更推荐使用ConcurrentHashMap。
  3. TreeMap
    • 数据结构：基于红黑树实现，键值对按照键的自然顺序或者自定义的Comparator进行排序。
    • 特点：有序性（按键排序）；键的唯一性。
    • 性能：添加、删除和查找操作的性能为O(log n)。
    • 使用场景：适用于需要按照键的顺序访问键值对的场景，如排序、范围查找等。
  4. ConcurrentHashMap
    • 数据结构：基于哈希表实现，通过分段锁或者CAS+Synchronized技术来保证线程安全。
    • 特点：无序性；键的唯一性；线程安全；高性能并发操作。
    • 性能：在多线程环境下，ConcurrentHashMap提供了比HashTable更高的并发性能。
    • 使用场景：适用于多线程环境下需要快速查找、添加和删除键值对的场景。它是HashMap的线程安全替代方案，通常比HashTable更受欢迎。

Queue 常用的子类

  1. LinkedList
    • 数据结构：基于双向链表实现。
    • 特点：
      • 支持队列操作（如入队、出队）。
      • 可以作为双端队列（Deque），支持从两端进行插入和删除操作。
    • 性能：
      • 入队和出队操作：O(1)，由于链表结构，操作效率高。
      • 随机访问：O(n)，由于需要从头开始遍历链表。
    • 使用场景：适用于需要进行频繁的插入和删除操作的场景，比如任务调度、消息传递等。
  2. PriorityQueue
    • 数据结构：基于优先级堆（通常是二叉堆）实现。
    • 特点：
      • 元素根据自然排序或者自定义的Comparator进行排序，优先级高的元素先被处理。
      • 不支持空元素。
    • 性能：
      • 入队操作：O(log n)，因为需要维护堆的结构。
      • 出队操作：O(log n)，同样需要维护堆的结构。
    • 使用场景：适用于需要处理具有优先级的元素的场景，如任务调度、事件管理等。
  3. ArrayDeque
    • 数据结构：基于动态数组实现，支持双端队列（Deque）操作。
    • 特点：
      • 可以用作队列（FIFO）或双端队列（从两端插入和删除）。
      • 不支持null元素。
    • 性能：
      • 入队和出队操作：O(1)，由于底层数组的双端操作效率较高。
      • 扩容开销：当容量不足时，需要重新分配更大的数组并复制元素。
    • 使用场景：适用于需要双端操作的场景，如实现栈、队列等数据结构，或者需要快速插入和删除操作的情况。
  4. ConcurrentLinkedQueue
    • 数据结构：基于非阻塞的链表（使用CAS技术实现）进行并发操作。
    • 特点：
      • 线程安全，适用于并发环境。
      • 先进先出（FIFO）顺序。
    • 性能：
      • 入队和出队操作：O(1)，使用无锁算法来保证并发性能。
    • 使用场景：适用于多线程环境中的队列操作，如任务队列、消息队列等。

特性 LinkedList PriorityQueue ArrayDeque ConcurrentLinkedQueue

性能 入队/出队操作 O(1)；随机访问 O(n) 入队/出队操作 O(log n) 入队/出队操作 O(1) 入队/出队操作 O(1)

根据实际需求选择合适的Queue实现类，可以在不同场景下优化性能和功能。LinkedList适用于双端操作，PriorityQueue适用于需要优先级处理的任务，ArrayDeque适用于高效的双端操作，ConcurrentLinkedQueue适用于并发环境中的安全操作。

ThreadLocal

当使用 ThreadLocal 时，每个线程都有一个独立的变量副本。这些副本是线程本地的，因此它们的内存地址是线程隔离的。在实际使用中，这些副本的值取决于以下几个方面：

  1. 初始值：
    • 当线程首次访问 ThreadLocal 变量时，如果这个变量还没有被初始化，ThreadLocal 类会调用其 initialValue() 方法来提供一个初始值。这个值通常是根据实现者的需求定义的。如果 initialValue() 方法没有被重写，ThreadLocal 默认会返回 null。
    • 例如，如果 initialValue() 被重写为返回一个新创建的对象，那么每个线程都会得到一个不同的对象实例作为其变量副本的初始值。
  2. 线程特定的值：
    • 每个线程对 ThreadLocal 变量的修改仅影响该线程自己的副本。其他线程的副本不会受到影响。因此，一个线程对 ThreadLocal 变量的设置或修改不会影响到其他线程中该变量的值。
    • 例如，如果线程 A 将 ThreadLocal 变量的值设置为 ObjectA，而线程 B 将其值设置为 ObjectB，那么线程 A 和线程 B 的 ThreadLocal 变量各自指向不同的对象实例。
  3. 值的获取：
    • 当一个线程调用 ThreadLocal 的 get() 方法时，它会返回该线程在当前 ThreadLocal 实例中的值。如果该线程之前没有为 ThreadLocal 变量设置值，则会调用 initialValue() 方法来生成一个值。
    • 例如，如果线程 A 调用 get() 方法，并且线程 A 已经为 ThreadLocal 变量设置了值 ObjectA，那么 get() 方法将返回 ObjectA。
  4. 内存地址和对象值：
    • 每个线程的 ThreadLocal 变量副本所指向的内存地址是线程私有的。因此，不同线程中的 ThreadLocal 变量副本指向不同的内存地址。
    • 如果你在每个线程中设置了不同的值，那么这些值存储在不同的内存位置，不会互相干扰。每个线程对 ThreadLocal 变量的 get() 和 set() 操作都只作用于线程自己的副本。

总结

ThreadLocal 确保每个线程都有一个独立的变量副本，其内存地址是线程特有的。变量的值由每个线程单独设置和获取，因此，线程 A 和线程 B 的 ThreadLocal 变量值和内存地址彼此独立。

B树和B+树简介

B树

B树是一种平衡查找树，它被设计用来支持在节点上进行高效的多关键字查找操作。B树的每个节点可以存储多个关键字，并且可以有多个子节点。

  • 高度平衡：B树通过保持每个分支子树的数量大致相同来平衡树的高度，这样可以减少搜索的深度。
  • 节点结构：B树节点包含关键字和指向子节点的指针。对于非叶子节点，关键字用于分割子树；对于叶子节点，关键字用于查找数据。
  • 插入和删除：B树维护平衡的方式是插入或删除节点时重新分配关键字和调整子树。
  • 查找效率：B树的查找效率是O(log n)，这里的n是节点数量。

B+树

B+树是B树的一种变种，它通常用于存储和检索大型数据集合。B+树的节点也是平衡的，但其结构有一些特别的调整。

  • 所有数据在叶子节点：B+树的非叶子节点仅用来指示关键字所在的子树，叶子节点存储所有的数据和指向下一个叶子节点的指针，形成有序的链表。
  • 叶子节点间的连接：叶子节点通过指针相连，这样可以有效地实现范围查询、顺序访问和快速遍历。
  • 非叶子节点只存储关键字：B+树的非叶子节点只存储关键字和子节点的指针，不存储数据，使得每个节点可以存储更多的关键字，减少树的深度。
  • 查找效率：像B树一样，B+树的查找效率也是O(log n)。

为什么MySQL使用B+树

MySQL使用B+树的原因如下：

  • 范围查询：B+树的设计使得对范围查询特别有效，因为所有数据都在叶子节点上，并且通过指针有序排列。
  • 顺序访问：B+树的连续叶子节点通过指针相连，可以实现快速的顺序扫描。
  • 空间效率：B+树的非叶子节点不存储数据副本，减少了内存使用，节省了存储空间。
  • 缓存友好：由于B+树的数据集中在叶子节点，这些节点通常会被加载到内存中，提高数据访问的速度。
  • 更好的增删改查性能：因为B+树通常使用较少的节点数，所以能够提供更快的插入和删除操作。

在MySQL中，B+树特别适用于索引数据，例如 InnoDB 和 MyISAM 存储引擎都使用B+树来管理索引，以支持高效的查询操作。
